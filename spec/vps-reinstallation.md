# Подготовка чистой переустановки VPS

Решение пользователя от 17 сентября 2026 года: переустановить существующий VPS,
не заказывать второй. После обследования пользователь запустил переустановку
на Ubuntu 26 по прежнему адресу. Сервер отвечает с новым SSH host key;
точная версия ОС и готовность проверяются после сверки fingerprint через панель.
Сайт v8std.ru остаётся на GitHub Pages.

## Результат обследования до переустановки

Ubuntu 24.04.3 LTS, x86_64, 1 CPU, около 1 ГБ RAM без swap, диск 15 ГБ
(занято около 3,3 ГБ). Docker не установлен; MCP работает как systemd-сервис.
Текущее потребление MCP около 234 МиБ, наблюдавшийся peak около 260 МиБ.
На хосте также размещён сайт 0x1c.ru (/var/www/0x1c.ru, около 11 МБ),
работают nginx, fail2ban и Zabbix. Переустановка затронет все эти службы.
В панели показано уведомление о временной недоступности создания резервных копий.
Провайдерские снимки пока не подтверждены. Внешняя файловая копия скачана на машину
оператора: 5880 записей, 48 434 135 байт; читаемость архива и наличие конфигурации,
данных MCP, сайта 0x1c.ru и SSH-настроек проверены, SHA256 сохранён рядом с архивом.
Это не полный образ диска; восстановление работоспособного хоста ещё не проверено.
Лимит 1,5 ГБ в локальном Compose не доказывает необходимый размер RAM сервера:
решение о тарифе принимается по проверке кандидата и расходу памяти при обновлении.

## Что необходимо до стирания диска

1. Установить точный идентификатор VPS в панели и сверить его с SSH-хостом.
   Инвентаризировать сервисы, диски, nginx, systemd и контейнеры: наличие только
   v8std опровергнуто: сохранить также сайт 0x1c.ru. Размер диска, архитектура и ОС проверены выше.
2. Сделать снимок средствами панели и внешнюю копию конфигурации, данных,
   сертификатов, индексов, журналов и состояния release controller. Секреты хранить
   вне Git с ограниченным доступом. Копия на переустанавливаемом диске не подходит.
   Проверить читаемость копии и доступный в панели способ восстановления снимка.
3. Зафиксировать принятую версию исходников и digest обоих образов, доступных
   для скачивания без локального Docker-кэша. Не использовать локальные тестовые теги.
4. Согласовать время простоя и предъявить пользователю точный сервер, состав
   удаляемого и место резервной копии перед необратимым действием в панели.

## Публикация артефактов

Текущий workflow публикует только проверенный main. PR выполняет validate;
создание PR само по себе не публикует Docker-образы.
Все три флага MCP в GitHub сейчас выключены. Публикация образов и установка
сервиса — разные действия; флаг runtime остаётся выключенным до первичной приёмки.

Есть незакрытая зависимость первой поставки: при включённой публикации образов
и выключенной публикации корпуса prepare-pages требует уже существующий
публичный манифест и архив. При обследовании манифест вернул HTTP 404.
Поэтому включение одного флага образов не гарантирует
успешного первого выпуска. До стирания сервера нужно проверить доступность
манифеста и выбрать проверенный путь первичной публикации; не отключать эту
проверку и не выдавать частично опубликованные digest за принятый выпуск.

## После установки чистой ОС

Базовая ОС должна предоставить systemd, Python 3.12, Docker, nginx и инструменты
проверки аттестаций, требуемые release controller. Конкретные команды установки
зависят от выбранной ОС и добавляются после инвентаризации.

- Разместить проверенные файлы runtime и контроллера поставки из одного принятого SHA.
  Действующий путь контроллера: /opt/v8std-release/delivery/vps/v8std_mcp_release.py.
- Настроить root-owned policy на основе delivery/vps/release-policy.example.json,
  каталоги индексов и состояния, отдельный журнал, recovery units, ограниченный
  SSH-вход CI и sudoers из delivery/vps. Обновить known_hosts после переустановки
  только после проверки нового fingerprint через доверенный канал панели.
- Настроить TLS для ai.v8std.ru и include nginx из delivery/vps/nginx.
  Проверить nginx -t до открытия публичного маршрута.
- Разместить проверенный архив индекса, затем манифест. Проверить скачивание
  снаружи и совпадение digest, не опираясь на старый локальный кэш.
- Сформировать envelope и одноразовое разрешение initial-install.json, привязанное
  к его SHA256. Первичную установку выполняет root-оператор командой
  initial-install; обычный CI deploy не заменяет установку без предшественника.
- Проверить /healthz, /version, initialize, tools/list и фактическое чтение статьи
  через публичный адрес. Принять runtime только после public smoke.
- После приёмки подключить обычный rollout CI; провал приёмки означает восстановление
  из подготовленной копии, а не возврат DNS на несуществующий второй сервер.

## Незавершённые части

Нужны сверка нового SSH-ключа, проверка фактической версии Ubuntu 26,
проверка восстановления резервной копии и совместимости зависимостей с новой ОС.
Прежние данные об Ubuntu 24.04 выше описывают только сохранённую установку.
Независимый локальный Compose MCP, передача единого готового артефакта индекса и
изоляция выходов сборки также остаются в плане поставки. Этот PR может сохранить
сделанные разработки, но не должен объявлять всю целевую поставку завершённой.
