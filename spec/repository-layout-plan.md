# Разделение файлов и оставшиеся работы по поставке

План согласован 16 сентября 2026 года. Актуализирован 17 сентября по рабочему
дереву: перенос каталогов выполнен, но целевая поставка ещё не завершена.
Основание — [целевая поставка](delivery-target.md) и
[набор файлов сборки сайта](local-site-build-files.md).

```text
repository/

├── zensical.toml, retrieval-rules.yml
├── requirements.txt, requirements-build.lock
├── LICENSE, LICENSES/
├── runtime/                            MCP и его зависимости
├── delivery/
│   ├── index/                          упаковка индекса
│   ├── site/                           упаковка сайта и Dockerfile
│   ├── mcp/                            Dockerfile MCP
│   ├── ci/                             сборка и публикация артефактов
│   ├── vps/                            установка, обновление, возврат
│   └── local/                          Compose для готовых образов
├── dev/
│   ├── content/                        обновление исходного контента
│   ├── checks/                         проверки и бенчмарки
│   └── requirements-test.lock          зависимости проверок
├── tests/                              тесты и фикстуры
├── spec/                               внутренние описания и правила
└── .github/workflows/                  GitHub CI
```

- В `scripts/` находятся 14 файлов маршрута сборки сайта и установщик
  `install_zensical.sh`. В `data/` — два каталога диагностик для sitemap.
- Подготовка статей и четыре вспомогательных JSON находятся в `dev/content/`.
  Они не нужны для сборки уже подготовленного контента.
- Код MCP находится в `runtime/`, чтобы пакет проекта не перекрывал SDK `mcp`.
  Общие модули сборки, нужные runtime, остаются в `scripts/`.
- `delivery/vps/legacy-release-guard.conf` — systemd drop-in, а не nginx-конфигурация.
- Для разработки сайта используется нативное Python-окружение. Docker для
  разработки удалён. Dockerfile в `delivery/ci/` обслуживает сборку в CI.
- MCP использует только Streamable HTTP. stdio и Docker MCP Catalog/Gateway удалены.
- Прежний архитектурный процесс, `spec/archive/` и `dev/archive/` удалены.
  Сохранены [33 согласованных правила](architecture-review.md) с конкретными тестами.

Файл вне минимального набора HTML-сборки может быть необходим другим результатам
поставки. MCP, упаковка индекса и средства публикации остаются частями продукта.

## Связь с результатами поставки

| Результат | Код и конфигурация |
|---|---|
| Сайт на v8std.ru (GitHub Pages) | `scripts/`, `delivery/ci/`, GitHub workflow |
| Индекс на ai.v8std.ru (VPS) | Генераторы сайта, `delivery/index/`, `delivery/ci/`, `delivery/vps/` |
| MCP на ai.v8std.ru (VPS) | `runtime/`, `delivery/mcp/`, `delivery/vps/` |
| Docker локального сайта с индексом | `delivery/site/`, `delivery/index/` |
| Docker локального MCP | `runtime/`, `delivery/mcp/`, `delivery/local/` |

Таблица показывает ответственность кода, а не подтверждает опубликованный выпуск
или чистую переустановку VPS. Текущие команды контейнерного запуска описаны
в [инструкции](container-installation.md).

## Оставшиеся работы

### 1. Самостоятельный локальный MCP

Сейчас `delivery/local/compose.yaml` запускает сайт отдельно или сайт вместе
с MCP. Сервис MCP имеет `depends_on: site`, работает во внутренней сети,
а его порт публикуется через proxy сайта. Поэтому выбор публичного URL индекса
сам по себе не превращает этот Compose в самостоятельный MCP.

Добавить независимый запуск MCP с собственным портом и доступом к индексу
на `ai.v8std.ru`. Сохранить совместный режим с локальным источником без скрытого
перехода на публичный. Проверить все три режима: сайт, MCP, сайт с MCP.

### 2. Один подготовленный артефакт индекса

Сейчас CI вызывает `delivery.index.generate_mcp_snapshot`, а
`delivery.site.build_local_site` повторно вызывает `publish_snapshot`.
Воспроизводимость двух упаковок не равна требованию «собрать один раз».

Передавать готовый артефакт в упаковку сайта и публикацию на VPS.
Проверить совпадение digest и соответствие индекса версии страниц.

### 3. Выходы сборки отдельно от исходников

Обычный `scripts/zensical_docs.sh` пока пишет генерации в `docs/` и `overrides/`,
а готовый сайт — в `site/`. Изолированная упаковка локального сайта уже работает
на временной копии; это не означает изоляции обычной сборки разработчика.

Согласованное направление: подготовка в `.cache/build/`, результаты в
`dist/site/`, `dist/index/`, `dist/local-site/`. Эти пути ещё не реализованы
как общий маршрут. При изменении адаптировать и `build`, и `serve`, исключить
производные файлы из Git и проверить обновление страниц при редактировании.
Критерий: чистая сборка и просмотр работают без изменения исходных деревьев.

### 4. Выпуск и чистая переустановка VPS

По уточнению пользователя переустанавливается существующий VPS.
Подготовка описана в [плане переустановки](vps-reinstallation.md).
Наличие release controller не подтверждает готовность хоста.

Перед выпуском проверить итоговый кандидат: активные тесты, strict build,
оба образа и три режима локального запуска. Пять отключённых проверок,
перечисленных в [обзоре правил](architecture-review.md), не считать пройденными.
Прежние частичные прогоны не заменяют проверку итогового кандидата.

Публикацию и действия на production выполнять в пределах разрешений
[AGENTS.md](../AGENTS.md). Завершение — фактическое выполнение всех критериев
[целевой поставки](delivery-target.md), включая чистую установку VPS и общий индекс.
