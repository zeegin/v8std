# Архитектурные артефакты v8std, версия 3

## Область изменения

Версия 3 принимается с `design:mcp-clean-host-release-policy`. Машинная schema
не меняется. Все разделы [версии 2](architecture-artifacts-v2.md), включая
нормативно унаследованные разделы версии 1, сохраняются. Заменяется только
первый абзац «Границы публикации и MCP deployment» следующим уточнением.

## Первичная активация

Первичная активация требует отдельного согласованного операционного этапа:
точный target, проверенные артефакты main, защищённые GitHub branch/environment,
изолированные credentials, работающий host recovery и явное включение.
Режим перехода определяется принятой архитектурой:

- При замене существующего deployment обязательны предусмотренные этим режимом
  backup/restore и predecessor.
- При явно выбранной владельцем чистой переустановке без возврата старой ОС
  полный VM backup, legacy restore и отдельная предварительная репетиция не
  требуются. До стирания новая поставка и нужная история публикации сохраняются
  вне host. Агент останавливается перед остановкой MCP и ждёт отдельного
  подтверждения оператора после уведомления потребителей. Согласие на
  подготовительный план не является этим подтверждением.

На чистом host первый runtime принимается отдельной операторской процедурой,
не через фиктивный predecessor. До принятия сбой означает maintenance или
необходимость ремонта новой установки, не обещанный возврат старой машины.
После принятия сохраняются обычные recovery/rollback автоматических updates.
Недоказанная old/new capacity не позволяет включить бесшовный runtime CI.
Отсутствие нагрузочной репетиции не является доказательством производительности.

Этот режим не даёт CI право переустанавливать ОС, удалять чужие приложения,
менять доступы или самостоятельно выбирать первый runtime. Секреты и settings
требуют своей согласованной операции. До остановочного подтверждения допускается
подготовка, но не downtime или переключение public MCP.

## Неизменные границы

Отдельная ветка до записи, основной checkout, письменный design и implementation
plan, запрет редактирования frozen main документов, semantic impact, все merge
gates и локальная интеграция сохраняются. Push main требует явного запроса.
Только после initial activation разрешённый push запускает настроенный CI
rollout проверенного SHA/digest, не произвольные ручные production mutations.

Контент по-прежнему публикуется archive-first, затем Pages manifest. Runtime
не собирается на production. Kill switch останавливает новые releases,
не выключает MCP и не обрывает recovery уже начатого обновления. Catalog review
не заменяет локальные gates или production acceptance и фиксируется отдельно.

Указатель loader, repo instructions, skill и tests переводятся на v3 согласованно
в implementation plan. Наличие этого нового документа до такого изменения
не считается выполненной миграцией инструментов или включённой автоматизацией.

## Публичное решение и закрытая эксплуатация

Документы `spec/` доступны в публичном Git-репозитории, хотя не включаются в сайт.
В них фиксируются требования, архитектура и общие процедуры, а не частные
адреса, идентификаторы инфраструктуры, сторонние приложения владельца, состояние
его доступов или детали переписки. Эти сведения хранятся вне репозитория в
закрытой операторской записи. Перед commit проверяются документы и примеры
наряду с кодом; для публикации проверяется также отправляемая история Git.
